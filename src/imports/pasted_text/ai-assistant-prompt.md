IMPROVE THE EXISTING AI ASSISTANT + ADD AN SOS FEATURE

Do NOT redesign or replace the existing website.
Keep all existing patient, caregiver, and doctor interfaces, games, Dear Diary, dashboards, navigation, colors, components, and functionality exactly as they are.
This prompt only refines the AI Assistant's conversational behavior and adds a new SOS/Emergency feature to the Patient interface.

============================================================
PART 1 — FIX THE AI ASSISTANT'S CONVERSATION QUALITY
============================================================

CURRENT PROBLEM:
The AI currently feels robotic and cold. It repeats the same canned response whenever the user says something that isn't a recognized command/intent (e.g. "play a game", "open diary"). It does not feel conversational, warm, or human — it feels like a rules-based chatbot with a few hardcoded replies.

REQUIRED FIX:
Rebuild the AI response logic so it behaves like a general-purpose conversational assistant (comparable to ChatGPT/Meta AI in tone and flexibility), specifically tuned for a warm, patient, dementia-friendly persona — NOT limited to a fixed set of recognized commands.

1. Always Generate a Real Response
- The AI must never fall back to a generic "I didn't understand" or repeat the same stock phrase for unrecognized input.
- Every message from the user — on-topic or not — should receive a natural, relevant, warm reply generated by the underlying language model, not a static/hardcoded string.
- If the input has nothing to do with the app (e.g. patient says "I miss my daughter" or "it's raining today"), the AI should respond conversationally and empathetically first, and only gently suggest an app action if it naturally fits — never force a redirect.
- If the AI truly doesn't have information (e.g. factual question it can't answer), it should say so warmly and simply, in one short sentence — never repeat a fixed error message.

2. No Repetition
- The AI must track recent conversation context so it does not say the exact same sentence twice in a row.
- Vary encouragement phrases, greetings, and clarifying questions naturally, the way a real person would.

3. Intent Detection Should Be a Layer, Not the Whole Brain
- Run every user message through two things in parallel/sequence:
  a) Conversational reply generation (LLM-based, natural language, warm tone) — this ALWAYS runs.
  b) Intent/navigation detection — a lightweight classifier that checks if the message matches an app action (see Part 2). This is additive, not a replacement for the conversational reply.
- If an intent is detected, the AI replies conversationally AND performs the navigation action (e.g. "Of course 😊 let's play together" + auto-navigate to Games).
- If no intent is detected, the AI still replies conversationally with no navigation — this is the case that is currently broken and must be fixed.

4. Tone & Personality (unchanged from original spec, reinforced here)
- Sweet, patient, warm, calm, friendly, respectful, encouraging, non-judgmental.
- Short, simple sentences appropriate for elderly dementia patients.
- Never say "you already asked that," "that's incorrect," "you failed," or anything that could make the patient feel bad.
- Never sound scripted or robotic — responses should read like a caring companion, not a form-response bot.

============================================================
PART 2 — VOICE VS. TEXT RESPONSE BEHAVIOR
============================================================

Fix the output mode so it matches how the patient is interacting:

- IF the patient uses the MICROPHONE (speaks to the AI):
  → The AI responds with BOTH voice (text-to-speech) AND an on-screen text bubble showing the same response.
  → Trigger the "AI speaking" animation state while voice plays.

- IF the patient TYPES a message (uses the keyboard/text input):
  → The AI responds with TEXT ONLY — no voice/audio output.
  → No "speaking" animation; just the response appearing in the chat bubble.

- The mode should be determined per-message by the input method the user just used, not a fixed global toggle — a patient can switch between typing and speaking within the same conversation, and each response should match how that particular message was sent.
- Keep the existing avatar states (idle / listening / processing / AI speaking) but only invoke "AI speaking" for voice-triggered exchanges.

============================================================
PART 3 — NAVIGATION SHOULD REMAIN ROBUST
============================================================

Keep and strengthen the existing navigation intents from the original AI Assistant spec:
- "Open my diary" → Dear Diary
- "I want to play a game" → Games
- "Play some Bihu music" → Music, filtered to Bihu/Assamese content
- "Show me my medicines" → Medication
- "Show my old memories" → Diary History
- "I want to talk to my caregiver" → Caregiver communication

- After navigating, the AI's chat should stay accessible (don't force-close the assistant) so the patient can keep talking if they want.
- If the AI isn't sure whether the patient wants to navigate somewhere, it should ask a warm clarifying question rather than guessing or ignoring it (e.g. "Would you like me to open your diary?").

PART 4 — AI GENDER / PERSONA CUSTOMIZATION (REINFORCE & INTEGRATE)
============================================================

The original spec included a basic male/female/neutral persona picker — make sure it is fully wired into the fixed conversational behavior above, not just a cosmetic setting.

1. Settings
- In AI settings (accessible from the AI chat screen or patient/caregiver settings), keep the existing picker:
  - 👩 Female
  - 👨 Male
  - 🧑 Neutral
- This selection should be stored per-patient in their profile, editable by the patient if they're able, and also editable by the caregiver.

2. What Changes With the Selection
- Voice (text-to-speech): switch the TTS voice to match the selected gender (male voice, female voice, or a neutral-sounding voice) — across every language the app supports (Assamese, Manipuri, Khasi, Bengali, Nagamese, English, Hindi). If a given language's TTS engine doesn't have a neutral option, fall back to the closest available voice and note this as a known limitation.
- Avatar: update the AI's visual avatar (idle/listening/processing/speaking states) to match the selected persona.
- Name (optional but recommended): allow the patient/caregiver to give the AI companion a simple name, shown consistently in the chat header and voice greetings.
- The gender/persona selection changes voice and appearance ONLY — it must NOT change the AI's tone, warmth, or personality traits from Part 1. All three persona options are equally sweet, patient, warm, and encouraging.

3. Consistency
- Once set, the persona (voice + avatar) should stay consistent across every screen where the AI appears — Patient chat, and the Caregiver/Doctor assistants if they also expose a persona picker.
- Switching persona mid-conversation should not reset or lose the conversation history.

============================================================
PART 5 — FIX: LANGUAGE SELECTION NOT APPLYING
============================================================

CURRENT PROBLEM:
The app has a multi-language selector (Assamese, Manipuri, Khasi, Bengali, Nagamese, English, Hindi) but choosing a different language does not actually change the displayed language — the UI stays in whatever language it started in.

REQUIRED FIX:
1. Centralize Language State
- There must be a single, global source of truth for the currently selected language (e.g. a shared i18n context/store), not separate/local language variables per screen or component.
- The patient's `preferred_language` field in their profile should initialize this global state on login/app load.
- Changing the language selector must update this ONE global state — every component reads from it, none should cache or hardcode a language independently.

2. Actually Re-render on Change
- Selecting a new language must immediately trigger a re-render of all currently visible text — labels, buttons, prompts, AI chat, game instructions, diary prompts, everything — without requiring a page reload or app restart.
- Audit every screen for hardcoded strings that bypass the translation system (e.g. text written directly in JSX/HTML instead of pulled from the i18n dictionary) — these are the most common cause of "language doesn't change" bugs. Replace all of them with translation keys.

3. Persistence
- Save the selected language to the patient's profile/local storage immediately on change, so it persists across sessions, app restarts, and offline use (per the existing offline-first requirement).
- On reconnect/sync, the language preference should sync to the backend along with other profile data.

4. Coverage — Make Sure ALL of These Actually Switch:
- All UI labels, buttons, and navigation text
- Game titles, instructions, and feedback messages
- Dear Diary prompts and confirmation messages
- AI Assistant conversational text AND voice (TTS) output (see Part 1 and Part 4 — the AI's replies and spoken voice must be in the currently selected language, not a default)
- Caregiver-facing transcriptions (should still default to patient's language, with an explicit toggle to view in English — per original spec)
- Error messages, empty states, and confirmation dialogs (these are the most commonly missed / hardcoded in English)

5. Mid-Session Switching
- If the patient switches language mid-session (e.g. mid-game or mid-AI-conversation), the currently open screen should update in place — don't require navigating away and back.
- Do not lose any in-progress data (e.g. a half-finished game, an in-progress diary recording) when the language changes.

6. Testing
- Test switching language from every screen that exposes the selector (patient settings, onboarding, caregiver control panel).
- Test that no screen is left showing a mix of two languages after a switch.
- Test that language selection persists after closing and reopening the app, and after an offline/online sync cycle.
- Test that the AI Assistant's text replies and voice output both correctly follow the newly selected language on the very next message, without needing to restart the conversation.

PART 6 — NEW FEATURE: SOS / EMERGENCY BUTTON (PATIENT INTERFACE)
============================================================

Add a dedicated SOS feature to the Patient interface, separate from the AI Assistant, always accessible.

1. Placement
- A clearly visible, large, high-contrast red "SOS" or "🆘 Help" button.
- Persistent across the Patient interface — e.g. fixed corner button or included in the main navigation — but positioned so it cannot be triggered by accidental taps during normal use (not stacked directly on top of frequently-tapped game buttons).
- Minimum 60x60px, following the same accessibility sizing standard as the rest of the patient UI.

2. Interaction Flow
- Patient taps the SOS button.
- Show a large, simple, unmistakable confirmation screen (to reduce accidental triggers) with two big buttons:
  - "Yes, I need help" (red, prominent)
  - "No, I'm okay" (calm, secondary)
- Auto-confirm after a short countdown (e.g. 5–10 seconds) if the patient doesn't respond, in case they're too distressed to tap — but allow cancellation up until the countdown ends.
- On confirmation:
  - Initiate a call to the patient's designated primary emergency contact (stored in patient profile — e.g. caregiver's phone number).
  - If the call cannot connect, fall back to the next listed emergency contact.
  - Simultaneously send an SOS alert (push notification + in-app alert) to the caregiver and doctor dashboards, including timestamp and, if permitted, the patient's last known location.
  - Show the patient a calm, reassuring confirmation message in their language: e.g. "Help is on the way ❤️. Stay with me."

3. Data & Settings
- Add an "Emergency Contacts" field to the patient profile (name, relationship, phone number, priority order) — editable by caregiver/doctor, not by the patient, to prevent accidental misconfiguration.
- Log every SOS event (timestamp, response time, whether confirmed or auto-triggered, outcome) in the same audit-logging system used elsewhere in the app, per the existing HIPAA-style compliance requirements.

4. Caregiver/Doctor Side
- SOS alerts appear as a high-priority, unmissable notification on both the Caregiver dashboard and Doctor dashboard — distinct visually from routine notifications (e.g. red banner, sound alert).
- Include a "Mark as resolved" action so caregivers/doctors can acknowledge and close out the alert once handled.

5. Safety Considerations
- The SOS flow must work even if the patient is mid-conversation with the AI Assistant or mid-game — it should always be reachable and always take priority over any other in-app activity.
- Keep the SOS interaction as simple as possible (minimum taps) since it will be used under distress — avoid multi-step menus beyond the single confirmation screen described above.
- Ensure SOS functions offline where possible (e.g. attempt a native phone call via the device's dialer even without internet; queue the caregiver/doctor alert to send once connectivity returns).
